# Deploying Duely

Goal: the app running at a public HTTPS URL your friends can use, for free.

## The production architecture

```
            Browser (your friends)
                   │  HTTPS
                   ▼
   ┌──────────────────────────────────────┐
   │ Render web service (Docker container) │
   │  uvicorn → FastAPI                    │
   │   /api/*   → routers → services → DB  │
   │   /*       → built React app (static) │
   └───────────────┬───────────────┬──────┘
                   │ SQL over TLS  │ HTTPS
                   ▼               ▼
          Neon (managed Postgres)  Brevo (email API)

   GitHub ── push ──▶ GitHub Actions CI (tests, lint, docker build)
          └─ push ──▶ Render auto-deploys the new image
   GitHub Actions "Daily reminders" ── 08:00 IST ──▶ POST /api/internal/reminders/run
```

| Piece | Service | Why this one | Free-tier caveat |
|-------|---------|--------------|------------------|
| App container | **Render** (web service, Docker) | Builds straight from the Dockerfile, HTTPS included, auto-deploy on push | Sleeps after ~15 min idle; the next visit takes up to a minute to wake |
| Database | **Neon** | Real Postgres, free tier with no expiry date, connection string just works | Storage limit on free plan; compute suspends when idle (wakes in ~1 s) |
| Email | **Brevo** | HTTP API (works where SMTP ports are blocked), lets you verify a single sender address without owning a domain | Daily send limit on the free plan |
| CI + daily trigger | **GitHub Actions** | Already where the code lives; scheduled workflows are free for public repos | Scheduled runs can start a few minutes late |

> Free-tier limits change over time. Check each provider's pricing page when you sign up.

Why one container instead of "frontend on Vercel, backend elsewhere"? The login cookie is
`SameSite=Lax`. If the page and the API were on two different sites, the browser would not send
the cookie with API calls and login would silently fail. Serving both from one origin avoids that,
and avoids CORS entirely. See `GUIDE.md` §6.

## Step-by-step (your part)

You create the accounts and paste secrets. Claude must not create accounts or handle your
passwords, so these steps are yours. Allow 30–45 minutes.

### 1. Push the code to GitHub
1. Create an **empty** repository on github.com (e.g. `duely`). Public is fine (it's
   a portfolio piece); `.env` is in `.gitignore`, so no secrets are pushed.
2. In this folder:
   ```bash
   git remote add origin https://github.com/<you>/duely.git
   git push -u origin main
   ```
3. Open the **Actions** tab: the **CI** workflow should go green.

### 2. Create the database (Neon)
1. Sign up at neon.tech → **Create project** → region close to your users (e.g. Singapore).
2. Copy the **connection string** (it looks like
   `postgresql://user:password@ep-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`).
   Keep it secret. You don't need to change `postgresql://`: the app adds the driver name itself.

### 3. Set up email (Brevo)
1. Sign up at brevo.com.
2. **Senders, domains & dedicated IPs → Senders → Add a sender**: use your own email address
   and click the verification link Brevo sends you.
3. **SMTP & API → API keys → Generate a new API key**. Copy it.

### 4. Create the web service (Render)
1. Sign up at render.com with your GitHub account.
2. **New → Blueprint** → pick the repository. Render reads `render.yaml` and proposes the
   `duely` web service.
3. Fill the values it asks for:

   | Variable | Value |
   |----------|-------|
   | `DATABASE_URL` | the Neon connection string |
   | `APP_URL` | `https://duely.onrender.com` (use the URL Render shows you) |
   | `FRONTEND_ORIGIN` | same as `APP_URL` |
   | `CRON_SECRET` | a long random string: `python -c "import secrets; print(secrets.token_urlsafe(32))"` |
   | `BREVO_API_KEY` | the Brevo API key |
   | `EMAIL_FROM_ADDRESS` | the sender address you verified in Brevo |

   `JWT_SECRET` is generated by Render automatically.
4. **Apply**. The first build takes a few minutes. When the container starts it runs
   `alembic upgrade head`, creating the tables in Neon, and then starts the server.
5. Open the URL → register → you're live.

### 5. Turn on daily reminder emails
1. GitHub repo → **Settings → Secrets and variables → Actions → New repository secret**:
   - `APP_URL` = your Render URL (no trailing slash)
   - `CRON_SECRET` = exactly the same value you gave Render
2. **Actions → Daily reminders → Run workflow** to test it now. In the app, turn on email
   reminders (Reminders page) and have something due today; you should get an email.

### 6. (Optional) Demo account for your resume
In Render → your service → **Shell**:
```bash
python -m app.scripts.seed_demo --email demo@example.com --password '<a password you choose>'
```
Put the demo login in your README so recruiters can click around.

## Deploy checklist (every release)

- [ ] CI is green on `main` (tests, lint, `alembic check`, docker build).
- [ ] New schema change? It's a **new** migration file; no applied migration was edited.
- [ ] Migration is backwards compatible with the running code (add columns as nullable or with
      a default; drop things in a later release).
- [ ] No secrets in the diff (`git diff --cached | grep -i secret`).
- [ ] After deploy: `GET /api/health` returns `{"status":"ok","database":"ok"}`.
- [ ] Log in, create a to-do and a finance entry, check Home.
- [ ] First deploy only: Render → **Logs** shows no `Header True-Client-IP missing` warning
      after a login. (If it does, rate limits are using the proxy's address: check with
      Render support which header carries the visitor IP and set `CLIENT_IP_HEADER`.)
- [ ] Rollback plan: Render → **Events** → redeploy the previous successful deploy.

## Environment variables (complete list)

| Name | Required | Default | Purpose |
|------|----------|---------|---------|
| `DATABASE_URL` | yes | – | Postgres connection |
| `JWT_SECRET` | yes | – | Signs login tokens (≥ 32 chars) |
| `ENVIRONMENT` | prod | `development` | `production` turns on `Secure` cookies, HSTS, and hides `/docs` |
| `APP_URL` | prod | `http://localhost:5173` | Links inside emails |
| `FRONTEND_ORIGIN` | prod | `http://localhost:5173` | CORS allow-list |
| `CLIENT_IP_HEADER` | prod | unset (connection address) | Header with the visitor's real IP, for rate limits. `True-Client-IP` on Render (set in render.yaml). Never `X-Forwarded-For` |
| `CRON_SECRET` | for reminders | – | Protects the daily job endpoint |
| `EMAIL_PROVIDER` | for email | `console` | `console`, `smtp` or `brevo` |
| `BREVO_API_KEY` | if brevo | – | Brevo API key |
| `EMAIL_FROM_ADDRESS` / `EMAIL_FROM_NAME` | for email | – | Sender |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD` / `SMTP_STARTTLS` | if smtp | – | Any SMTP server |
| `CURRENCY` | no | `INR` | Currency shown everywhere |
| `APP_TIMEZONE` | no | `Asia/Kolkata` | What "today" means |
| `STATIC_DIR` | set by Dockerfile | – | Where the built frontend lives |

## Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| Deploy fails at `alembic upgrade head` | `DATABASE_URL` wrong, or Neon project suspended/deleted |
| Login "works" but you're immediately logged out | `ENVIRONMENT=production` over plain HTTP (cookie is `Secure`); use the https URL |
| Test email: "Could not send email right now." | Brevo key wrong, or sender address not verified |
| Daily reminders workflow fails with 401 | `CRON_SECRET` differs between GitHub and Render |
| First page load takes ~1 minute | Render free instance was asleep; normal |
